# PayFlow v0.15.0

PayFlow v0.15.0 adds generalized abuse protection for selected sensitive identity
and MFA workflows, bounded security observability, and reproducible developer-
workstation performance evidence without changing PayFlow's simulated-money
boundary.

PayFlow remains an educational simulated digital-wallet backend. It does not
process real money and is not certified for production financial use.

## Highlights

### Generalized abuse-protection policy

- the application-facing policy freezes five bounded workflow identifiers
- workflow policy remains independent from controllers, servlet APIs, and Redis adapters
- endpoint-specific windows, identity limits, client limits, and dependency-failure modes are validated at startup
- the trusted effective-client-address boundary is reused instead of trusting attacker-controlled forwarding headers
- the global generalized policy switch remains disabled by default so deployment activation is explicit

### Shared Redis enforcement

- one atomic Redis operation evaluates identity and trusted-client quota dimensions
- Redis keys use domain-separated fixed-length digests instead of raw identities or client addresses
- quota state is explicitly expiring, repairs missing TTLs, and remains bounded in cardinality
- real-Redis tests cover threshold boundaries, concurrency, expiry, and dependency failures
- `FAIL_CLOSED` and `FAIL_OPEN` behavior is explicit per workflow; changing failure mode requires security review

### Protected workflows

- email-verification requests evaluate normalized identity and trusted-client quotas before account lookup
- password-recovery requests preserve the same anti-enumeration boundary
- both account-action request endpoints retain an empty `202 Accepted` response across eligible, ineligible, quota-limited, and fail-closed dependency outcomes
- MFA login-challenge confirmation enforces quota before challenge lookup or sensitive mutation
- step-up grant issuance enforces quota before user/authenticator locking, second-factor consumption, grant creation, or supersession
- blocked workflows do not consume valid single-use credentials or create protected side effects

### Observability and operations

- Micrometer decision and Redis-failure metrics use only bounded application-owned dimensions
- a dedicated Grafana dashboard covers protected-workflow outcomes and dependency health
- Prometheus alert rules cover sustained blocking, Redis dependency failures, and fail-open exposure
- the operations runbook documents investigation, rollback, false-positive handling, and safe mitigation
- observable output excludes email addresses, user identifiers, raw client addresses, credentials, Redis keys, counters, TTL values, and raw exception detail

### Performance evidence

- pinned external k6 tooling stays outside the normal Maven lifecycle
- representative protected workflows have reproducible steady, saturation, overload, quota-pressure, and recovery scenarios
- accepted evidence satisfies the frozen developer-workstation contract, including zero quota bypass in the documented quota-pressure checks
- the bounded registration experiment did not demonstrate material resource exhaustion through the tested 16 registrations/second ceiling
- performance results are environment-specific engineering evidence and are not production-capacity certification

## Registration decision

Registration remains deliberately unwired from generalized abuse protection in
v0.15.0 under the evidence-backed `DEFER` decision. The existing registration
`201` / `400` / `409` public contract is unchanged. The validated registration
policy definition remains available for a future separately reviewed decision,
but configuration presence does not imply endpoint wiring.

A future `ACTIVATE` decision requires new evidence and a separately reviewed
implementation/comparison checkpoint. v0.15.0 does not claim absence of risk
above the tested range.

## Compatibility and security boundaries

- the existing password-login limiter remains a separate compatibility contract with unchanged counters, keys, limits, public behavior, and metrics
- generalized account-action quota decisions preserve anti-enumeration semantics
- MFA challenge quota rejection reuses the existing coarse unauthorized boundary
- fail-closed generalized dependency failure for MFA and step-up reuses the existing `MFA_SECURITY_UNAVAILABLE` boundary
- TOTP values, recovery codes, challenge credentials, step-up grants, account-action credentials, and their digests remain outside quota state and observable output
- registration activation, active-authenticator replacement, CAPTCHA, external bot detection, WAF/API-gateway deployment, adaptive ML risk scoring, frontend work, and real-money operation remain outside v0.15.0

## Database and upgrade notes

- v0.15.0 introduces no new Flyway migration; the schema remains at V24
- PostgreSQL remains the system of record
- Redis is required for generalized enforcement when the deployment switch is enabled
- the generalized protection switch remains disabled by default and must be activated deliberately after deployment configuration review
- existing JWT, refresh-session, MFA, account-action mail, wallet, transfer, ledger, outbox, Kafka, and operator-audit contracts remain compatible
