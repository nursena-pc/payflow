# PayFlow v0.16.0

PayFlow v0.16.0 is a feature-frozen stabilization release focused on recovery
rehearsals, migration safety, `/api/v1` compatibility, dependency-failure
operations, documentation alignment, supply-chain evidence, and repeatable
clean-environment release verification.

PayFlow remains an educational simulated digital-wallet backend. It does not
process real money and is not certified for production financial use.

## Highlights

### Frozen `/api/v1` compatibility boundary

- the implemented public surface remains frozen at 30 canonical method/path operations across 28 normalized paths
- OpenAPI, Postman, README, and architecture documentation were reconciled with that source-backed surface
- deliberately coarse authentication, authorization, status/error, idempotency, anti-enumeration, and single-use security semantics remain compatibility-sensitive for the v1 line
- registration remains under the evidence-backed `DEFER` decision, and the existing password-login limiter remains a separate unchanged compatibility contract

### PostgreSQL recovery and migration rehearsals

- a repeatable PostgreSQL 17 backup/restore procedure restores into a clean isolated target rather than overwriting the source
- restore verification covers Flyway history and representative durable identity/session/wallet/transfer/ledger/outbox/dead-letter/audit state without committing dump contents or sensitive values
- the complete Flyway V1-through-V24 chain is rehearsed against a clean database
- an approved previous-release schema/data baseline is rehearsed through the forward migration chain to V24
- migration recovery documentation explicitly relies on the separate backup/restore boundary rather than claiming automated down-migrations, PITR, or production RPO/RTO certification

### Redis and Kafka outage/recovery operations

- Redis outage/recovery is rehearsed without weakening the existing fail-closed login-security contract
- registration abuse protection remains disabled under `DEFER`
- PostgreSQL remains the durable system of record while Redis remains bounded, expiring abuse-control state
- Kafka outage/recovery is rehearsed across the transactional outbox and dead-letter/replay boundaries
- durable PostgreSQL outbox and dead-letter state is retained across broker unavailability, and recovery uses existing retry/replay semantics without creating duplicate financial movement

### Dependency and supply-chain evidence

- committed-content secret scanning, vulnerability review, SBOM generation, and local build/provenance evidence are repeatable and tied to reviewed commits
- the reviewed dependency remediation removed the identified Critical/High release blockers; the release evidence does not claim that the dependency graph has zero vulnerabilities
- reviewed Gitleaks evidence preserves the existing deliberate/false-positive baseline while requiring zero new committed-content locations
- Maven Wrapper, Docker builder/runtime images, and security-analysis tooling are pinned where required by the reviewed evidence
- local provenance is explicitly not a SLSA, signing, reproducible-build, attestation, or production-certification claim

### Clean-environment release rehearsal

- release rehearsal starts from a detached clean checkout with no pre-existing `target/` or `.runtime/` output
- Maven Wrapper 3.9.16 and Java 21 are verified before the complete Maven suite runs
- executable JAR/checksum generation, committed security evidence, required-configuration fail-fast behavior, and production-profile Docker smoke are exercised without creating a tag or GitHub Release
- synthetic JWT keys are isolated in a Docker-managed volume owned by runtime UID 10001; ordinary developer service ports are not required by the rehearsal
- generated evidence excludes credentials, private keys, raw application logs, personal data, and environment-specific secret values

## Verification

- the merged Increment 7 clean-environment checkpoint passed 1,622 Maven tests with zero failures, errors, or skipped tests
- exact-head GitHub `CI` #262 and `Docker Smoke` #60 passed before Increment 7 merged through PR #185
- the release-finalization candidate must again pass complete Maven verification, executable JAR/checksum verification, committed secret/vulnerability/SBOM checks, and production-profile Docker smoke before its PR is eligible to merge
- immutable tag target, release workflow run, published artifact size, and independently verified published SHA-256 are recorded only after actual publication

## Compatibility and security boundaries

- Java 21
- Spring Boot 3.5.16
- PostgreSQL 17 with Flyway schema V24
- Maven Wrapper 3.9.16
- the frozen `/api/v1` request/response/error/authentication boundary remains compatible with the reviewed v0.16 stabilization baseline
- registration remains `DEFER`; no generalized registration limiter is activated by this release
- password-login limiter counters, keys, limits, public behavior, and metrics remain unchanged
- existing MFA, JWT rotation, refresh-session, account-action, wallet, transfer, ledger, outbox, Kafka, dead-letter, operator-audit, and observability semantics are not redesigned by v0.16.0

## Explicit non-goals

- new wallet, transfer, payment, or API capabilities
- registration activation or abuse-protection retuning
- login-limiter semantic changes
- new MFA factors, OAuth/OIDC, WebAuthn/passkeys, or active-authenticator replacement
- historical Flyway migration rewrites or automated down-migrations
- Kafka/outbox/dead-letter/replay redesign
- microservice extraction, Kubernetes, gateway, CDN, or WAF deployment redesign
- v1.0.0 publication
- artifact signing, SLSA claims, reproducible-build guarantees, provenance attestation, regulatory or production certification, production capacity guarantees, or real-money operation
