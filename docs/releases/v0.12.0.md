# PayFlow v0.12.0

PayFlow v0.12.0 adds a bounded JWT signing-key provider and an operationally
safe active/previous RSA verification overlap for controlled key rotation.

PayFlow remains an educational simulated digital-wallet backend. It does not
process real money and is not certified for production financial use.

## Highlights

### Stable key identification

- every newly issued access token carries the configured active `kid`
- key identifiers use a strict, bounded 64-character alphabet
- signing and verification remain pinned to RS256
- issuer, subject, email, role, lifetime, and public API payload contracts remain unchanged

### Active and previous verification overlap

- the active RSA key signs new access tokens and verifies active-key tokens
- one optional previous public key verifies unexpired tokens during a bounded rotation window
- the previous key is verification-only and cannot issue new tokens
- missing, unknown, duplicated, or untrusted key identifiers fail authentication
- duplicated key IDs and aliased RSA key material are rejected

### Configured production key loading

- PKCS#8 private-key and X.509 public-key resources are loaded through a dedicated adapter
- RSA keys shorter than 2,048 bits are rejected
- startup proves that the configured active private and public keys form one pair
- the `production` profile fails closed when required locations, identifiers, or key material are invalid
- process-local ephemeral keys remain limited to explicit non-production development mode

### Provider boundary

JWT issuance and verification depend on an adapter-local `JwtKeyProvider`
contract instead of owning key generation or resource loading. The boundary can
support a future KMS or HSM adapter without introducing provider-specific types
into PayFlow application or domain code.

## Security boundaries

- private keys, PEM content, and runtime key directories remain outside source control, container images, logs, metrics, and public errors
- verification accepts only the active and immediately previous configured public keys
- algorithm negotiation, symmetric signing, and JWT encryption are not introduced
- there is no dynamic key reload, remote KMS/HSM integration, or public JWKS endpoint in this release
- access-token revocation and refresh-token contracts are unchanged

## Upgrade notes

- No database migration is included.
- Existing authentication, authorization, wallet, transfer, ledger, outbox, Kafka, dead-letter, audit, and observability business rules are unchanged.
- Existing access-token claims and public request/response payloads are unchanged.
- Non-production development keeps the process-local ephemeral provider unless configured otherwise.
- Production deployments must provide one active PKCS#8 private key, its X.509 public key, and a stable active key identifier.
- During rotation, deploy the new active key with the former active public key as previous, retain overlap for at least the access-token TTL plus deployment skew, and then retire the previous key.
