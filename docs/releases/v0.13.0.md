# PayFlow v0.13.0

PayFlow v0.13.0 adds email-ownership verification, secure password recovery,
and a protected transactional mail-delivery boundary for account actions.

PayFlow remains an educational simulated digital-wallet backend. It does not
process real money and is not certified for production financial use.

## Highlights

### Email ownership verification

- new registrations begin with an unverified email while pre-v0.13.0 users are backfilled as verified
- registration issues one verification credential in the same PostgreSQL transaction
- generic request responses do not disclose whether an identity exists, is active, or is already verified
- confirmation consumes one opaque credential and marks ownership exactly once
- unverified users are rejected only after the submitted password is proven correct

### Password recovery

- generic recovery requests preserve the same anti-enumeration response boundary
- confirmation reuses the registration password-strength and BCrypt policy
- the recovery credential is consumed, the password hash is replaced, and every active refresh-token family is revoked atomically
- session revocation records use the dedicated `PASSWORD_RECOVERY` reason
- already-issued access JWTs retain only their existing short residual lifetime

### Opaque account-action credentials

- credentials contain 256 bits of cryptographically secure randomness
- canonical unpadded Base64 URL encoding is used at the delivery boundary
- digest-only persistence stores fixed-length SHA-256 digests
- email-verification and password-recovery purposes have separate lifetimes
- supersession is serialized per user and purpose
- pessimistic locking guarantees single-use consumption with one concurrent winner
- invalid, expired, consumed, superseded, and malformed recovery credentials share one public failure contract

### Secure transactional mail outbox

- verification and recovery mail records are persisted in the credential transaction
- SMTP delivery occurs only after commit and cannot roll back valid user state
- provider-ready mail bodies are protected with AES-256-GCM before persistence
- authenticated encryption binds protected content to message, user, purpose, recipient, and subject context
- workers claim rows with PostgreSQL leases and `FOR UPDATE SKIP LOCKED`
- retry is bounded and never scheduled beyond credential expiry
- stable `Message-ID` values reduce provider-side ambiguity while retaining a documented bounded duplicate risk
- protected content is erased after success, terminal failure, supersession, or expiry
- recipients, links, credentials, digests, and protected bytes remain outside logs and metrics

## Security boundaries

- account-action plaintext exists only in short-lived application memory needed to construct trusted delivery content
- request host headers never influence verification or recovery links
- production startup requires configured RSA signing material and a configured 32-byte mail-content protection key
- SMTP provider acknowledgements do not provide an exactly-once guarantee
- access-token denylisting, MFA, email-address changes, and remote KMS/HSM integration are not introduced
- purpose-specific Redis request quotas are deferred to the later generalized abuse-protection milestone
- v0.13.0 does not claim provider-side exactly-once delivery or generalized API-wide rate limiting

## Database migrations

- Flyway V15 adds `email_verified_at` and constrained digest-only account-action credential persistence
- Flyway V16 adds the `PASSWORD_RECOVERY` refresh-session revocation reason
- Flyway V17 adds the protected mail outbox, lease state, retry metadata, and terminal-content retention rules
- migration tests cover upgrades from the V13, V14, V15, and V16 baselines to the latest schema

## Upgrade notes

- Apply Flyway migrations through V17 before serving v0.13.0 traffic.
- Existing users are backfilled as email verified to prevent migration lockout.
- Newly registered users must confirm email ownership before login.
- Production deployments must configure account-action confirmation URIs, SMTP settings, and a Base64-encoded 32-byte mail-content protection key.
- Mail outbox workers require stable unique worker identifiers when multiple instances run.
- Existing wallet, transfer, ledger, Kafka, dead-letter, audit, observability, JWT, and refresh-token public payload contracts remain compatible.

## Compatibility

- Java 21
- Spring Boot 3.5.16
- PostgreSQL with Flyway schema V17
- Redis remains required for the existing login-rate-limit boundary
- Kafka contracts remain compatible with v0.12.0
- SMTP is exercised locally through Mailpit in the Compose application profile
