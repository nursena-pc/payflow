# PayFlow v0.14.0

PayFlow v0.14.0 adds TOTP multi-factor authentication, digest-only login
challenges and recovery codes, purpose-bound step-up authorization, and
transactional account-security mutations.

PayFlow remains an educational simulated digital-wallet backend. It does not
process real money and is not certified for production financial use.

## Highlights

### TOTP enrollment

- authenticated users begin enrollment by proving the current password
- secrets contain 160 bits of secure randomness and use canonical Base32
- provisioning follows RFC 4226/6238 with HMAC-SHA1, six digits, and 30-second steps
- pending and active secrets are protected with AES-256-GCM before persistence
- enrollment activates only after a valid proof within the bounded clock-skew window
- plaintext provisioning material is returned once and excluded from observable output

### MFA login challenge

- password verification remains the first factor
- enabled MFA returns `202 MFA_REQUIRED` without issuing access or refresh credentials
- PostgreSQL stores only challenge digests, expiry, attempt budget, and terminal state
- valid TOTP or one unused recovery code consumes the challenge exactly once
- concurrent confirmation permits at most one credential-issuing winner

### Recovery codes

- activation generates ten independent 128-bit canonical Base64URL codes
- only SHA-256 digests are persisted
- each code is pessimistically locked and consumed at most once
- rotation requires an exact purpose-bound step-up grant
- replacement plaintext is returned once with `Cache-Control: no-store`

### Step-up authorization

- grants contain 256 bits of secure randomness
- only SHA-256 digests are stored
- grants bind subject, exact purpose, issue time, expiry, consumption, and supersession
- wrong-subject, wrong-purpose, expired, superseded, malformed, unknown, and replayed grants share stable coarse errors

### MFA disable

- `DELETE /api/v1/users/me/mfa` derives ownership from the JWT subject
- the operation requires an exact `mfa-disable` step-up grant
- authenticator and recovery-code state are deleted atomically
- active refresh-token families are revoked with `MFA_DISABLED`
- credential-free audit evidence is appended in the same transaction

## Security boundaries

- MFA credentials and protected secret material never enter logs, metrics, traces, errors, or audit payloads
- client requests cannot provide or override the account identifier
- recovery-code and TOTP login failures remain indistinguishable
- step-up validation and consumption remain application-service responsibilities
- production requires a dedicated configured MFA secret-protection key
- active-authenticator replacement is not included; it requires a separately designed two-stage lifecycle
- generalized API-wide abuse protection remains a later milestone

## Upgrade notes

- Apply Flyway migrations through V24 before serving v0.14.0 traffic.
- Configure the production MFA AES-256-GCM secret-protection key.
- Existing users remain in the `DISABLED` MFA lifecycle until they enroll.
- Existing email, wallet, transfer, Kafka, JWT, refresh-session, and mail contracts remain compatible.
- Access JWTs already issued before MFA disable retain only their existing short residual lifetime.
