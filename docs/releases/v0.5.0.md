# PayFlow v0.5.0

Release date: 2026-07-23

## Overview

PayFlow v0.5.0 introduces a secured operations control plane for controlled Kafka dead-letter administration.

The release adds operator-only query, replay, and discard workflows while preserving the existing public wallet, transfer, and transaction APIs.

## Highlights

### Operations authorization

- Introduces the `PAYFLOW_OPERATIONS` authority.
- Grants operations access only when the authenticated JWT contains the exact `role=ADMIN` claim.
- Rejects anonymous requests with `401 Unauthorized`.
- Rejects authenticated non-operator requests with `403 Forbidden`.
- Keeps operator identity server-controlled by deriving its UUID from the JWT subject.

### Kafka dead-letter query API

Authorized operators can:

- list dead-letter records with deterministic pagination
- filter records by lifecycle status
- inspect one record by UUID
- review operational metadata without receiving Kafka payloads or record keys

Supported lifecycle statuses include:

- `RECEIVED`
- `REPLAYING`
- `REPLAYED`
- `REPLAY_FAILED`
- `DISCARDED`

### Controlled replay and discard commands

The release adds explicit command endpoints for:

- replaying a claimable dead-letter record
- idempotently discarding an eligible dead-letter record

Replay remains outside a long-running database transaction so Kafka publication is not coupled to an open PostgreSQL transaction.

Command outcomes are mapped to stable HTTP responses for:

- missing records
- invalid lifecycle transitions
- Kafka publication failures
- unresolved replay outcomes
- unavailable auditing
- unexpected internal failures

### Durable operator audit trail

Authorized replay and discard attempts now produce correlated append-only audit records.

Each command writes:

1. an `ATTEMPTED` audit row before execution
2. a `COMPLETED` audit row after execution

Audit records contain:

- audit record UUID
- command UUID
- operator UUID
- dead-letter record UUID
- command type
- command stage
- safe outcome
- timestamp

Audit records never contain:

- Kafka payloads
- Kafka record keys
- JWTs or access tokens
- operator email addresses
- exception messages
- stack traces
- replay lease owners

PostgreSQL constraints enforce valid command, stage, and outcome combinations. Updates and deletes against the command-audit table are rejected at database level.

If the initial audit record cannot be persisted, the command fails closed and is not executed.

## Operations API

| Method | Endpoint | Description |
|---|---|---|
| `GET` | `/api/v1/operations/kafka/dead-letters` | Lists paginated dead-letter operational metadata. |
| `GET` | `/api/v1/operations/kafka/dead-letters/{recordId}` | Returns authorized operational details for one record. |
| `POST` | `/api/v1/operations/kafka/dead-letters/{recordId}/replay` | Replays a claimable dead-letter record. |
| `POST` | `/api/v1/operations/kafka/dead-letters/{recordId}/discard` | Discards an eligible dead-letter record. |

All four endpoints require a bearer JWT that resolves to `PAYFLOW_OPERATIONS`.

## Database changes

### V11 — dead-letter query indexes

Adds indexes supporting:

- deterministic dead-letter listing
- lifecycle-status filtering
- operational query ordering

### V12 — command audit trail

Adds the append-only `kafka_dead_letter_command_audits` table with:

- command and stage uniqueness
- explicit enum-style allowlists
- stage/outcome consistency constraints
- operator and record lookup indexes
- update/delete rejection trigger

Flyway applies both migrations automatically during application startup.

## Postman

The Postman collection now contains a separate `Operations` folder with requests for:

- dead-letter listing
- record details
- replay
- discard

The operations workflow intentionally requires manually supplied local values:

- `operatorAccessToken`
- `deadLetterRecordId`

Both committed environment values remain empty. Live operator JWTs must never be committed or included in a shared exported environment.

## Compatibility

The operations control plane is additive.

No existing public authentication, user, wallet, transfer, or transaction-history endpoint is removed or renamed.

## Upgrade notes

1. Back up the PostgreSQL database according to the deployment environment's normal operational procedure.
2. Deploy the application with Flyway enabled so migrations V11 and V12 are applied.
3. Ensure the trusted JWT issuer supplies `role=ADMIN` only for authorized operators.
4. Do not place live operator JWTs in source-controlled configuration.
5. Import the updated Postman collection and populate privileged variables only in a private local environment.
